📦 1. System Overview

The WeldBot Diagnostic Agent is a multi-agent, LLM-powered diagnostic system that monitors 47 welding robots across 3 sensor types (wire_feed_speed, wire_temperature, welding_current). It follows a Planning-First workflow driven by DSPy (Declarative Self-Improving Python) and a skill system providing the LLM with domain-specific diagnostic sub-routines. A strict Human-in-the-Loop (HITL) gate ensures safety for all high-severity actions.

🔄 2. Agent Pipeline: Triage → Diagnostic → Systemic

🎯
Triage Agent

First-line filtering of incoming incidents from the L1/L2 poller. Classifies into three decisions:

DecisionCondition
CRITICAL_ESCALATEseverity_hint == "critical"
QUEUE_FOR_DIAGNOSTICSURGE / DROPOUT / INSTABILITY family
OR anomaly_score >= 0.5
AUTO_RESOLVEL2 events with anomaly_score < 0.5

Source: backend/app/robot_agent/agent/triage_agent.py

🧠
Diagnostic Agent

Central per-robot orchestrator. Runs the Planning-First workflow in two phases:

Phase 1 — Plan: LLM calls load_skill("create-plan") → generates an 8-task roadmap via PlanManager.

Phase 2 — Execute: LLM calls DSPy tools sequentially (load_skill, query_pm_cards, hitl_check, update_task_status) to gather evidence and reach a diagnosis.

State machine: idle → running → completed | blocked | failed

Source: backend/app/robot_agent/agent/diagnostic_agent.py

🌍
Systemic Agent

Second-tier escalation when multiple robots fail simultaneously (alert storm). Uses a DSPy signature to distinguish:

  • ✅ Systemic causes — e.g. central pump failure, power fluctuation, line-wide contamination
  • ❌ Isolated failures — independent per-robot issues

Outputs: reasoning, root_cause_candidate, recommended_action, is_systemic

Source: backend/app/robot_agent/agent/systemic_agent.py

📜 3. AGENTS.md — The Core Agent Instructions

The agend_knowledge/AGENTS.md file serves as the system prompt for the Diagnostic Agent's DSPy LLM. It defines the agent's role, the full 7-phase workflow, the skill catalog, available tools, and strict operational rules.

Agent Role Definition

"You are the Diagnostic Agent for the Welding Robot Anomaly Detection System. Your job is to diagnose signal anomalies from 4 welding robots (R-00 to R-03) across 3 sensors and produce structured incident reports."

Complete Workflow (7 Phases)

Phase 1
Plan→ Phase 2
Execute Tasks→ Phase 3
Verify Defect→ Phase 4
Correlate History→ Phase 5
Check FMEA→ Phase 6
HITL Gate→ Phase 7
Complete

Strict Rules

#Rule
1Plan First — Never attempt diagnosis without a roadmap from create-plan
2Sequential Task Completion — Call update_task_status for every task in order (1→8)
3Multi-Step Tasks — One plan task may require multiple DSPy turns
4Manual Status Guard — System does not auto-mark tasks (except prerequisite catch-up)
5No Premature End — Never call complete until ALL tasks are done
6Mandatory Final Summary — complete must include diagnosis, root cause, evidence, recommendations
7HITL Before High-Severity — CRITICAL/HIGH actions require hitl_check approval

🧩 4. Skill System

Skills are Markdown files stored under agent_knowledge/skills/<name>/SKILL.md. Each skill encapsulates a diagnostic sub-routine. The agent loads skills at runtime via load_skill().

📋
create-plan

Generates the structured 8-task diagnostic roadmap from _template.md. ALWAYS called first.

Required tools: load_skill

🔍
diagnose

Central diagnostic skill. Contains hard-coded sensor-based routing rules to direct incidents to the correct reference:

sensor == "wire_feed_speed" → references/wire_feed_speed.md
sensor == "wire_temperature" → references/wire_temperature.md
sensor == "welding_current" → references/welding_current.md

Each reference contains: failure modes, signal patterns, inspection checklists, PM card keywords, and severity tables.

Required tools: query_pm_cards, query_sensor_stats

✅
verify-defect

Checks if signal anomaly caused actual product surface defects via NDT/visual inspection systems. Separates signal-level anomalies from real quality issues.

Used after diagnosis confirms significant anomaly
Required tools: query_db

📅
correlate-history

Searches historical PM Cards and maintenance records to find similar past incidents and their resolutions. Cross-references same robot, sensor, and failure mode.

Used after loading diagnose skill
Required tools: query_pm_cards

⚙️
check-fmea

Cross-references the diagnosed anomaly against the FMEA (Failure Mode and Effects Analysis) knowledge base. Validates failure modes and identifies RPN and known mitigations.

Used before final recommendations
Required tools: query_pm_cards

📖
Sensor References

Three deep-dive sensor references auto-routed by the diagnose skill:

  • diagnose/references/wire_feed_speed.md
  • diagnose/references/wire_temperature.md
  • diagnose/references/welding_current.md

Each includes failure modes, signal patterns, inspection checklists, PM keywords, and severity tables.

🛡️ 5. Human-in-the-Loop (HITL) Safety System

🛡️
HITL Rules (hitl-rules.md)

Governs what the Diagnostic Agent may and may not do autonomously.

Action Severity Classification

Action TypeSeverityHITL Required
Read-only queries (SQL, RAG)LOWNo
Diagnostic reasoningLOWNo
Create draft reportLOWNo
Push to hitl_queueMEDIUMNo (auto)
Send notification (email/slack)HIGH✅ Yes
Update robot configHIGH✅ Yes
Dispatch maintenanceCRITICAL✅ Yes
Override safety interlockCRITICAL⛔ NEVER
📤
HITL Queue Protocol

When the agent proposes a HIGH/CRITICAL action, the system:

  1. Blocks immediate execution
  2. Logs to hitl_queue (SQL table) with status PENDING
  3. Preserves full context (incident_id, robot_id, action, reasoning)
  4. Emits SSE event via AgentEventEmitter
  5. Blocks up to 300s waiting for human resolution

Resolution Outcomes

StatusMeaningAgent Behavior
APPROVEDHuman says GORetries the action
REJECTEDHuman says NOAbandons, logs, continues reasoning
EXPIREDTimeout >24hAbandons, escalates
PENDINGAwaiting reviewWaits (max 24h)
H
hitl.py

Core HITL decision logic:

  • BLOCKED_ACTIONS — permanently blocked actions (never overridable)
  • ACTION_SEVERITY — severity lookup table
  • hitl_check() — evaluates action and returns ALLOWED | BLOCKED | PERMANENTLY_BLOCKED
  • DB-backed: inserts pending entries into hitl_queue table
🔐
hitl_gate.py

Synchronous blocking gate wrapping hitl.py:

  • Uses threading.Event to block agent until human resolves
  • 300-second timeout
  • SSE event emission via AgentEventEmitter
  • Simulation state integration for testing
🌐
api/hitl_api.py

REST endpoints for HITL management:

  • GET /api/hitl/pending — list pending approvals
  • POST /api/hitl/{queue_id}/approve — approve action
  • POST /api/hitl/{queue_id}/reject — reject action
  • SSE streaming for real-time HITL requests

Inputs (fed to LLM each turn):

  • system_prompt — AGENTS.md content
  • incident_context — Current incident details
  • loaded_skills — Skills loaded so far
  • available_skills — Full skill catalog

  • reasoning — Thought process
  • action — Tool to call
  • action_input — Tool argument

💡 13. Key Design Patterns

🔄
Planning-First Architecture

Every incident follows a strict Plan → Execute → Verify → Correlate → FMEA → HITL → Complete pipeline. The LLM cannot deviate — it must create a plan first, then execute tasks sequentially. This prevents hallucinated diagnoses and ensures traceability.

🎭
Skill-as-Markdown Pattern

Domain knowledge lives in Markdown files, not in code. Each skill is a self-contained diagnostic sub-routine loaded at runtime. This enables non-developers (domain experts) to update diagnostic procedures without touching Python code.

🛡️
HITL Gate (Circuit Breaker)

The HITL system acts as a circuit breaker — any HIGH/CRITICAL action is automatically blocked, logged, and queued for human approval. A threading.Event blocks the agent until resolution (300s timeout). Permanently blocked actions are architecturally rejected.

📡
Event-Driven SSE Broadcasting

AgentEventEmitter decouples agent internals from the transport layer. External code (SSE endpoints) hooks into callbacks (on_step, on_hitl_request, on_plan) to push real-time updates to the frontend.
